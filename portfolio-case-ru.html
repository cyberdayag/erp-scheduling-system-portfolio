Контекст и проблема

После начала работы в научно-образовательном центре физики и химии я обнаружил, что организация работает на тяжёлой системе, построенной на базе Excel. Она постоянно падала, зависала под нагрузкой и делала ежедневные операционные изменения крайне болезненными и подверженными ошибкам.

Масштаб операционной нагрузки:
26 школ-партнёров до 50 уроков в день 105 учебных групп специализированные лаборатории частые замены преподавателей, отмены и переносы уроков заказы оборудования

Опыт работы с транзакционными системами сформировал простой принцип: любое изменение расписания или ресурсов должно обрабатываться так же строго, как банковская операция. Поэтому я спроектировал систему, гарантирующую целостность на уровне СУБД, неизменяемый Audit Log и возможность безопасного отката (rollback) любого дня.

Моя роль

Изучив бизнес-процессы центра, я самостоятельно спроектировал архитектуру системы: модель данных, ключевые бизнес-инварианты, ролевую модель доступа, механизмы разрешения конфликтов. Также спроектировал схему деплоя (AWS EC2 + Cloudflare Tunnel) и процесс резервного копирования (AWS S3) с проверенным восстановлением после полного сбоя.

С AI я работал как техлид с командой разработчиков: ставил задачи, определял решение каждой из них, пошагово проверял код на каждом шаге, прежде чем принять его в систему.

Полноценная ERP-платформа для управления расписанием и операционной деятельностью:

  • Годовой шаблон + генерируемое годовое расписание
  • Редактирование расписания на уровне дня с freeze / unfreeze / rollback
  • Замены учителей
  • Отмены и переносы уроков
  • Создание новых уроков и дополнительных занятий
  • Процесс заказа лабораторного оборудования
  • Очередь заявок (принцип «одного окна»)
  • Гранулярный ролевой доступ
  • Коридорные ТВ-табло для учителей и учеников
  • Полностью неизменяемый audit log

Технологический стек:

PostgreSQL 16 PL/pgSQL Node.js + Express Vue 3 + PrimeVue (RTL) Docker · AWS · Cloudflare Tunnel
  • PostgreSQL — выбран ради нативной поддержки EXCLUDE USING GIST. Это позволяет на уровне движка СУБД гарантировать отсутствие пересечений временных интервалов и автоматически исключать race conditions при параллельных запросах.
  • Логика в БД — перенос инвариантов в СУБД обеспечил единый источник правды и целостность данных независимо от точки подключения (API, фоновые скрипты или прямые админ-сессии).
  • Node.js + Express — тонкий stateless-шлюз (Thin API Gateway), ограниченный задачами авторизации и транзита запросов без дублирования бизнес-логики.
  • Vue 3 + PrimeVue — сократил time-to-market за счёт готовой экосистемы сложных UI-компонентов для административных экранов.
  • Cloudflare Tunnel — изолировал инфраструктуру по принципу Zero Trust, полностью исключив необходимость публикации публичного IP и открытия входящих портов.

Интерфейс системы

Нажмите на любой скриншот, чтобы открыть его в полном размере.

Дневной Гантт — актуальное расписание дня по кабинетам. Цветовая кодировка предметов, подсветка замен, индикатор текущего времени.
Годовой шаблон (Basic Schedule) — источник правды. Изменения из него безопасно распространяются на сгенерированное годовое расписание с помощью двухфазного алгоритма.
Дашборд учителя — личный кабинет: ближайшие уроки, заявки на оборудование, история замен и рабочий график.
Админ-дашборд — центральное «одно окно». Учителя только создают заявки, администраторы рассматривают, корректируют и применяют изменения.
Дашборд лаборантов — операционная витрина: заказы оборудования и заметки на выбранный день.
Audit Log — полностью неизменяемая история всех значимых действий. Даже суперадмин не может изменить или удалить записи.
Табло для учеников — публичный экран с текущим расписанием.

Инженерная культура — код и документация

Один из ключевых принципов проекта: логика и решения объясняются прямо в коде — не только что делает функция, но и зачем она нужна и что сломается, если нарушить инвариант.

1. Чёткое разделение структуры и бизнес-логики

schema.sql — явное правило: здесь только структура. Бизнес-логика живёт в модульных файлах.

2. Подбор кабинетов с явными бизнес-правилами

campus._find_room() — правила приоритета кабинетов для физики и химии задокументированы и закодированы прямо в запросе.
year_schedule.sql — в шапке файла объясняется назначение каждой ключевой функции и поток freeze / unfreeze дня.
